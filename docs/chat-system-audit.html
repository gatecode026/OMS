OMS Chat System — Cross-Platform Architecture & Synchronization Report

A read-only audit of the React web, React Native mobile, and Node.js/MongoDB/Redis/Socket.IO backend chat stacks — mapping structure, data flow, feature parity, and every synchronization fault that stops Web and Mobile from behaving as one enterprise messaging platform.

Scope frontend/ · mobile/ · backend/src/modules/chat Chat LOC audited ≈37,000 Method static repository analysis Code changed none

00 Executive Summary

Web and Mobile are not architecturally identical — they are two independently-built clients that talk to a shared backend and socket contract, but diverge in state ownership, offline strategy, virtualization, and call signaling. The backend is the source of truth and is the most mature layer. The most urgent risks are a duplicate/dead mobile call-signaling path, no message virtualization on Web, and no shared event/feature contract, which lets the two clients drift silently.

Top findings at a glance

CRIT Two call systems on Mobile

Live WebRTC uses correct call:signal:* events; a parallel CallSignalingManager listens for call:offer/answer/ice-candidate/busy — events the backend never emits. Dead, misleading, and a maintenance trap.

CRIT Web renders every message

No react-window/virtualization anywhere in frontend/. Long conversations mount thousands of DOM nodes; Mobile uses FlashList.

HIGH No shared contract

Socket event names + payloads are hand-maintained in three places. Backend emits both message:new and new_message; clients pick different ones.

HIGH Divergent offline models

Web: localStorage failed-message cache. Mobile: OfflineQueueManager (secureStore) + a bespoke fileCacheService React-Query persister. Neither shares logic.

MED State ownership asymmetry

Web = single 2,973-line React Context (35 useState). Mobile = React Query + 4 Zustand stores. No server-state layer on Web.

MED Web feature lag

Drafts, scheduled messages, and broadcast surfaces exist on Mobile/backend but are absent or thin on Web.

01 Architecture Overview

One backend, one socket gateway, two clients built to different philosophies. The backend owns truth (MongoDB) and ephemeral state (Redis); clients subscribe over Socket.IO and reconcile via REST.

Web (React SPA)

  • State: one ChatContext.jsx (2,973 LOC, 35 useState, useReducer-free) owns conversations, messages, typing, presence, calls.
  • Server state: none — no React Query/SWR. Every fetch is manual and lives in memory; lost on refresh.
  • Rendering: plain .map() lists, no virtualization.
  • Offline: failed messages cached to localStorage (chat_failed_msg_*) with retry; no send queue.

Mobile (RN / Expo 57)

  • Server state: TanStack Query, keys ['chat','conversations'], ['chat','messages',convId]; custom disk persister via fileCacheService.
  • Client state: 4 Zustand stores (call, message-action, realtime, shared-media).
  • Rendering: FlashList (virtualized).
  • Offline: OfflineQueueManager (secureStore) flushes on reconnect; SyncManager/ConflictResolver present.
  • Service layer: 29 "Manager" services — powerful but 5 are dead (§12).

Backend

  • Layering: chat.controller.js (1,312) → chat.service.js (2,061) → repositories (message.repository.js, conversation.repository.js) with a repositoryContract.js security guard and per-tenant plugin.
  • Sub-domains modularized: threads, polls, search, pinned, presence, typing, read-receipts each have their own service/controller/routes.
  • Multi-tenant: every model carries companyId + tenantPlugin; indexes are company-scoped.
  • Redis: presence (presence:user:*, 120s TTL + in-memory fallback), typing (typing:conversation:*), company online sets (presence:company:*).

Root cause

No generated/shared event enum. Each side string-literals event names, so typos and renames survive silently until a feature "just doesn't update" on one platform.

Dual naming

Backend emits both colon-style (message:new, user:online) and snake-style (new_message, user_online) — an unfinished migration. Redundant emits waste bandwidth and confuse consumers.

Acknowledgements

send_message, heartbeat use ack callbacks (good). Most broadcasts are fire-and-forget with a missed_events replay on reconnect as the safety net.

08 Media Pipeline

Backend / storage

  • ImageKit CDN; signed auth via /imagekit/auth; server-side upload via utils/imagekit.js.
  • Message media{} stores url, fileName, size, mime, width/height, duration, imageKitFileId/FilePath for later deletion.
  • Types: text · image · file · audio · system · emoji · call · poll.

Clients

  • Mobile: UploadManager + useUploadQueue (retry, progress), DownloadManager, AttachmentCacheManager (dead), fileCacheService.
  • Web: upload inside MessageInput.jsx; direct ImageKit + message_upload_error socket fallback.
  • Gap: no thumbnail/transcode step server-side; clients render full media. Compression is client-only and asymmetric.
MED-M1MEDIANo shared upload contract → asymmetric retry/compression

Mobile has a durable upload queue with retry; Web uploads inline with a single error event. Large-file behavior, compression quality, and retry semantics differ per platform.

10 Performance Analysis

CRIT Web message list

No virtualization — a 5k-message thread mounts 5k bubbles. Scroll jank + memory growth. Mobile's FlashList proves the fix is known internally.

HIGH Web context re-renders

One 2,973-LOC provider with 35 useState → any message updates re-render every consumer. No selector/memo isolation like Zustand gives Mobile.

MED Mobile message query

useQuery not useInfiniteQuery for messages → whole list refetched instead of paged windows.

GOOD DB indexing

Message/conversation indexes are company-scoped and cover the hot paths (list, pinned, search text index).

GOOD Redis presence

120s TTL keys + in-memory fallback avoid a hard Redis dependency for online status.

MED Redundant socket traffic

Dual event names (message:new+new_message, user:online+user_online) double some broadcasts.

11 Prioritized Issue Register

CRIT-1CRITICALMobile has two call-signaling systems; one binds events the backend never emits

Root cause: a legacy CallSignalingManager was kept alongside the live useWebRTC hook. It subscribes to call:offer, call:answer, call:ice-candidate, call:busy — none exist server-side (backend emits call:signal:*). Impact: dead handlers, risk of double-registration and missed hangup/hangup-race if ever re-enabled. Repro: place a call from web → mobile; the manager's listeners never fire while useWebRTC's do.

mobile/.../services/CallSignalingManager.ts:76-83 · useWebRTC.ts:249,340,396,472 (correct) · backend chat.socket.js:2255 emits call:signal:offer
CRIT-2CRITICALWeb renders all messages — no virtualization

Evidence: zero matches for react-window/react-virtual/virtuoso across frontend/src. Impact: long conversations degrade to unusable; memory climbs with history depth. Business impact: power users (support, ops) with large threads hit the worst experience.

frontend/src/pages/chat/ChatWindow.jsx — plain list render · MessageBubble.jsx 1222 LOC per-item
HIGH-1HIGHNo shared socket-event / payload contract across three codebases

Event names are string literals maintained by hand in backend, web, and mobile. Renames and typos surface only as "feature silently doesn't sync." Poll, thread, reaction-remove, and conversation-sync gaps all trace here.

HIGH-2HIGHWeb server-state lives in one Context with no cache layer

Impact: full refetch on mount, no request dedupe/stale management, whole-tree re-renders, state lost on refresh. Mobile already proves the React Query pattern in-house.

HIGH-3HIGHIncomplete conversation-management & poll realtime on Web

Web omits several conversation:* sync events and granular poll:* events that Mobile handles → multi-device actions (archive on phone, vote on phone) don't reflect on an open web tab until refresh.

MED-1MEDIUMReaction-remove not handled on Web

Web binds reaction_added but not reaction_removed/reaction:updated → a reaction removed elsewhere lingers on the web view.

MED-2MEDIUMTwo offline models, no shared reconciliation

Web localStorage failed-cache vs. Mobile secureStore queue + disk-persisted React Query. Conflict resolution (ConflictResolver) exists only on Mobile.

MED-3MEDIUMDual event-naming convention on backend

Unfinished snake_case→colon migration leaves duplicate emits (new_message/message:new, user_online/user:online).

LOW-1LOWFour REST aliases for one upload handler

/upload · /attachments · /media · /files → same function; obscures client usage and widens surface.

14 Final Verdict — the 10 Questions

  1. Are Web & Mobile architecturally identical? No. Same backend contract, but Web = React Context (no server cache, no virtualization); Mobile = React Query + Zustand + service layer + FlashList.
  2. Web-only features? None of note — Web is a subset. (Web-specific: web-push subscription flow.)
  3. Mobile-only features? Drafts, scheduled-message surface, broadcast stub, richer location/contacts, durable offline queue + conflict resolution.
  4. Partially implemented? Delete-for-everyone (both), Web reactions/polls/conversation-sync realtime, Mobile threads realtime & infinite pagination, broadcast/channels (stub only).
  5. Broken sync paths? Web poll events, Web reaction-remove, Web conversation-management multi-device, Mobile thread realtime, Mobile phantom call events.
  6. Inconsistent caches? Web has no server-state cache; Mobile disk-persists React Query. Presence/unread derived independently per client → drift.
  7. Missing/mismatched socket events? Backend dual-names (message:new/new_message); Web misses reaction_removed + granular poll:* + several conversation:*; Mobile binds non-existent call:offer/answer/ice-candidate/busy.
  8. APIs behaving differently? Reactions & deletes: Web via REST, Mobile via socket → different failure/latency profiles; 4 upload aliases.
  9. What blocks perfect real-time sync? Absence of a single shared event/payload contract, plus asymmetric client state models — every gap above is downstream of these two.
  10. What architectural change unifies them? (a) One versioned socket-event + payload contract consumed by all three; (b) React Query as the shared server-state layer on both clients with socket→cache patches; (c) shared offline-outbox + conflict semantics; (d) delete duplicate/dead mobile services and Web virtualization gap. That converges the two clients onto one enterprise platform behavior.
